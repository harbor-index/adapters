# HumanEvalPack → Harbor Adapter

## Overview

This adapter converts [HumanEvalPack](https://huggingface.co/datasets/bigcode/humanevalpack), the benchmark of the OctoPack paper ([arXiv:2308.07124](https://arxiv.org/abs/2308.07124)), into Harbor tasks. HumanEvalPack extends the 164 HumanEval problems to six languages (Python, JavaScript, Java, Go, C++, Rust) and three task types. One Harbor task is one problem of one task type in one language.

| Task family (upstream task) | Harbor task ids | What the agent does | Generated by default | Tasks |
|---|---|---|---|---|
| HumanEvalFix (`humanevalfixtests-<language>`) | `fixtests-<language>-<n>` | repairs a buggy function, given the unit tests | yes | 981 |
| HumanEvalSynthesize (`humanevalsynthesize-<language>`) | `synthesize-<language>-<n>` | writes a function from its signature and docstring | yes | 981 |
| HumanEvalFixDocs (`humanevalfixdocs-<language>`) | `fixdocs-<language>-<n>` | repairs a buggy function, given the docstring instead of the tests | no (`--subsets fixdocs`) | 981 |

- **Default dataset: 1,962 tasks** (981 + 981). Per family: 164 tasks each for Python, JavaScript, Java and C++, 162 for Go and 163 for Rust. The task ids use `javascript` for the dataset config `js`.
- The dataset has 164 problems per language (984 in total). Three problems are left out of every family because the benchmark's own reference solution does not pass the original harness reliably: `Go/27`, `Go/95` and `Rust/32` (see [Notes & Caveats](#notes--caveats)).
- **HumanEvalExplain is not adapted.** It chains two model calls (explain the code, then re-implement it from the explanation alone), which does not map onto a single agent task.
- Task type: single-function code repair and code synthesis. Metric: pass@1 (each task's reward is 0 or 1).
- Sources and pins: dataset `bigcode/humanevalpack` at revision `9a41762f73a8cb23bb5811b73d5aab164efcf378` (MIT license); task definitions from [bigcode-evaluation-harness](https://github.com/bigcode-project/bigcode-evaluation-harness) at commit `8fc5bae6479c4fbbb28c3f8b644f6a15b3f3b5bd` (`bigcode_eval/tasks/humanevalpack.py`); scoring by the `code_eval_octopack` metric at commit `fee8e8d8ff689a4489e153233778dd36f865e7aa`.

**Relation to the existing `humanevalfix` adapter.** This repository already contains `src/humanevalfix`, which covers the Python part of HumanEvalFix only (164 tasks) in the form in which OpenHands evaluates it: its instruction is the OpenHands prompt, the agent edits a prepared file, and its parity experiments were run against the OpenHands evaluation harness. This adapter instead reproduces the original bigcode-evaluation-harness tasks (its prompts and its scoring code) for all six languages and for HumanEvalSynthesize as well. The 164 `fixtests-python-*` tasks here are built from the same 164 dataset rows as the tasks of `humanevalfix`; they differ in the instruction wording, in what is submitted (a new solution file) and in the scoring code. The two adapters are separate datasets: do not add their scores, and do not count the Python Fix problems twice when reporting both.

## What is HumanEvalPack?

HumanEvalPack was introduced in "OctoPack: Instruction Tuning Code Large Language Models" (Muennighoff et al., 2023). It covers the 164 HumanEval problems in six languages, and the authors added a bug by hand to every reference solution, which gives three task types per language: HumanEvalFix (fix the bug), HumanEvalExplain (explain the code, then synthesize it from the explanation) and HumanEvalSynthesize (write the function from its signature and docstring). A problem counts as solved when the produced function passes the problem's unit tests; the metric is pass@1, reported per language and as the average over the six languages. The original harness is bigcode-evaluation-harness: a model completes a prompt, and the `code_eval_octopack` metric compiles and runs the completion together with the tests.

## Adapter Features

- **The original prompts, verbatim.** `upstream.py` is a port of the prompt construction of the harness (the default `instruct` prompt format). The prompt is embedded unchanged in a fenced block of `instruction.md`; the text around it only says where to save the answer and how it is graded.
- **The original scoring code.** `tests/execute.py` is a byte-identical copy of the metric's `execute.py` (sha256 `2143dc31471b777b37214376b9b48ec95baf5b00e501a8b9bff6bff96d267b4a`, see `tests/execute.NOTICE.txt`), so compile commands, run commands and timeouts are the original ones (Python 10 s, JavaScript 10 s, Java 10 s, Go 20 s, C++ 60 s, Rust 300 s). `tests/verify.py` ports the per-language preprocessing of `process_results` for a single generation and then calls that executor.
- **One toolchain image per language**, with the versions the OctoPack README lists where it lists them: Python 3.9.13, Java 18, Go 1.18.4, g++ 11.4.0, Rust 1.71.1 and js-md5 0.7.3 (see [Notes & Caveats](#notes--caveats) for the deviations). All tasks of a language share one build context, so an image is built once per language.
- **Offline tasks.** Images contain everything the tests need (NumPy, js-md5, the testify packages for Go, pre-built Rust crates). The agent phase and the verifier both run with `network_mode = "no-network"`. Building the Go image does not use a Go module proxy.
- **Separate verifier.** Scoring runs in a fresh container built from the same image (`[verifier] environment_mode = "separate"`); the solution file is the only artifact a task declares.
- **Untrusted submissions.** The verifier compiles and runs the submitted code under an unprivileged account, in its own session, under the original time limit plus a hard kill, and removes every process of that account before the reward is written.
- **Generator.** Deterministic output (same bytes and file modes on every run), tasks built in a staging directory and renamed into place, an exclusive lock on the output directory, `--overwrite`, `--limit`, `--task-ids`, `--subsets`, `--languages`, and a seeded, stratified `--split parity`.
- **Per-language scores.** `humanevalpack-score` computes pass@1 per language and task family from a job directory, as the paper reports it.
- No custom agent is added.

## Run Evaluation / Harness

All commands below use Harbor 0.25.0 and are run from the repository root.

### Running with Datasets Registry

The dataset is not registered yet, so the registry commands cannot be run today; they are listed for the time after registration.

```bash
# Oracle agent (reference solutions)
harbor run -d bigcode/humanevalpack

# A specific agent and model
harbor run -d bigcode/humanevalpack -a <agent_name> -m "<model_name>"
```

### Using Job Configurations

```bash
# Generate the tasks (see "Usage: Create Task Directories"), then run the oracle over the whole dataset
harbor run -c src/humanevalpack/run_humanevalpack.yaml

# Another agent and model with the same configuration
harbor run -c src/humanevalpack/run_humanevalpack.yaml -a <agent_name> -m "<model_name>"

# Without a configuration file
harbor run -p datasets/humanevalpack -a <agent_name> -m "<model_name>"

# Resume an interrupted job, or run again the trials that ended with a given error
harbor job resume -p jobs/<job-name>
harbor job resume -p jobs/<job-name> -f <ErrorType>
```

Results are written to `jobs/<job-name>/`.

### Running Individual Trial

```bash
harbor trial start -p datasets/humanevalpack/fixtests-python-0
harbor trial start -p datasets/humanevalpack/fixtests-python-0 -a <agent_name> -m "<model_name>"
```

### Per-language and per-family pass@1

Harbor reports one mean reward over all trials of a job. The paper reports pass@1 per language for each task family and the unweighted mean over the six languages. To get these numbers from a job:

```bash
cd src/humanevalpack
uv run humanevalpack-score ../../jobs/<job-name>
uv run humanevalpack-score ../../jobs/<job-name> --json scores.json
```

The script takes exactly one job directory. If a trial has no verifier result (the environment did not start, scoring broke, the job is unfinished), it lists these trials and exits with status 1 instead of printing scores; `--allow-unscored` prints the partial numbers. If a job holds several trials of one problem, the score of the problem is the fraction of its trials that passed; use one job per run to get one score per run. Because `Go/27`, `Go/95` and `Rust/32` are not part of the dataset, the Go and Rust numbers are computed over 162 and 163 problems and are not directly comparable with published numbers over 164.

## Usage: Create Task Directories

```bash
cd src/humanevalpack
uv sync
uv run humanevalpack                                   # writes ../../datasets/humanevalpack (1,962 tasks)
uv run humanevalpack --output-dir /path/to/output      # another output directory
```

| Flag | Meaning |
|---|---|
| `--output-dir DIR` | Directory to write the task directories to (default: `datasets/humanevalpack` at the repository root) |
| `--limit N` | Generate only the first N tasks of the selection |
| `--overwrite` | Regenerate tasks whose directory already exists (they are skipped otherwise; an incomplete directory is an error that asks for `--overwrite`) |
| `--task-ids ID ...` | Only these tasks, e.g. `fixtests-python-0 synthesize-rust-163` (ids of any of the three families) |
| `--split full\|parity` | `parity` is a fixed, seeded subset with 20 problems per task family and language (240 tasks with the default families) |
| `--subsets NAME ...` | Any of `fixtests`, `synthesize`, `fixdocs` (default: `fixtests synthesize`) |
| `--languages NAME ...` | Any of `python js java go cpp rust` (default: all) |
| `--cache-dir DIR` | Hugging Face cache directory for the dataset download |

The first run downloads six parquet files (one per language) from the Hugging Face Hub. Errors (unknown task id, excluded problem, negative `--limit`, failed download, unreadable data, unwritable output directory, a second run writing to the same directory) end with a one-line message and a non-zero exit status.

### Oracle verification

The oracle was run over the whole default dataset with Harbor 0.25.0 on Docker (`run_humanevalpack.yaml` with `-n 6`):

| Tasks | Trials with reward 1 | Exceptions | Mean reward |
|-------|----------------------|------------|-------------|
| 1,962 | 1,962 | 0 | 1.000 |

- The run was interrupted once by a restart of the session that had started it, after 645 finished trials, and was completed with `harbor job resume`. The six trials that were in flight at that moment were run again; no trial was repeated because of a failure. The two parts took 38 minutes and 1 h 19 min on a machine with 16 CPUs.
- `humanevalpack-score` on that job reports 100.00% pass@1 for every language in both task families (981 problems each).
- The dataset on disk is the one this run used: a fresh generation with the same code is identical to it file for file.

The 981 HumanEvalFixDocs tasks (`--subsets fixdocs`) have **not** been run in full with the oracle: one run was stopped early, and the 114 trials that had finished (C++ tasks) all scored 1. Each of them has the same reference file and the same test files as the HumanEvalFix task of the same problem, byte for byte (compared for all 981 pairs); only the instruction and the task name differ. Twelve of them (two per language) went through Harbor in the no-submission control below. Treat this family as generated but not oracle-verified.

### Parity plan

The original harness generates with a model and has no agent support, so this is scenario 2 of the adapter guide: the original side is a fork with an agent runner.

- **Original side:** https://github.com/him1411/bigcode-evaluation-harness/tree/harbor-parity (directory `harbor_parity/`). For every task of the parity subset the runner builds the task's own image, runs the agent with the unchanged instruction under the task's limits and network policy, and takes the solution file as the single generation of that problem. The generations are scored by the harness's own task classes (`process_results` in `bigcode_eval/tasks/humanevalpack.py`) with its metric `code_eval_octopack`, in the task image of the language. The harness's `main.py` is not used, because it loads a model and scores the first rows of a dataset, not a selection of rows.
- **Harbor side:** `uv run humanevalpack --split parity --output-dir ../../datasets/humanevalpack-parity` (240 tasks: 20 problems per task family and language) and one `harbor run` per run with the same agent and model; scores from `humanevalpack-score`.
- **Runs:** 3 per side, one agent at a pinned version with one model, to be agreed with the Harbor team. Reported as mean ± sample SEM of pass@1 in percent over the 240 tasks, with the per-language breakdown as supporting data.

**Checked without a model.** Two agents that need no model were run on all 240 parity tasks on both sides, and the two sides were compared task by task:

- Reference solutions (`stub-oracle` in the fork, `oracle` in Harbor): 240 of 240 passed on both sides.
- No solution file (`stub-nop` in the fork, `nop` in Harbor): 1 of 240 passed on both sides (`CPP/23`, see [Notes & Caveats](#notes--caveats)).
- In both comparisons the files handed to the two scorers were byte-identical for all 240 tasks, and no task got a different verdict.

The real agent (`claude-code` 2.1.325) was also started on six tasks, one per language, on both sides with an invalid API key. On both sides it was installed and launched in every image (the installation adds Node.js from the distribution's packages in the five images that have none), reached the model endpoint under `no-network`, and stopped at the endpoint's authentication error (HTTP 401); Harbor then scored the missing file as 0. None of this is a parity result.

```bash
(cd src/humanevalpack && uv run humanevalpack-score ../../jobs/<job-name>)
```

Original side, from a clone of the fork (branch `harbor-parity`; its `harbor_parity/README.md` has the details). `<work>` is an empty directory:

```bash
python3 harbor_parity/prepare.py --harbor-dataset <adapters repo>/datasets/humanevalpack-parity --work-dir <work>
python3 harbor_parity/run_agent.py --work-dir <work> --candidate <run-name> \
```

## Notes & Caveats

**Excluded problems.** A task whose reference solution does not pass cannot have a reliable oracle, so three problems are left out of every task family:

- `Go/27`: the `prompt` field imports `strings`, the canonical solution never uses it, and Go rejects unused imports, so `prompt + canonical_solution` does not compile. In 200 runs of the reference test program, none passed.
- `Go/95`: the canonical solution depends on the iteration order of a Go map, which is random. In 200 runs of the reference test program, 157 passed and 43 failed.
- `Rust/32`: the canonical solution runs Newton's method on polynomials that the test draws from an unseeded random generator. In 300 runs of the compiled reference test program in the task image, 132 passed, 24 failed and 144 were still running after 10 seconds.

The other problems whose tests draw random inputs (32, 38, 50 and 53 in every language) were repeated 200 times each through the verifier with the reference solution: 4,600 verifications over 23 tasks, without a single failure.

**Upstream behaviour that is reproduced, not fixed.**

- `CPP/23` (`strlen`) passes with any submission, including an empty or missing file, in the original harness and here: its tests call the C library's `strlen`. The task is kept.
- For `Go/10`, `Go/32`, `Go/38` and `Go/50` the `declaration` field, which is what a HumanEvalFix prompt ends with, does not contain the helper function (`IsPalindrome`, `Poly`, `EncodeCyclic`, `EncodeShift`) that the `prompt` field defines and the solution or the tests use; for `CPP/38` the `declaration` field already contains the first lines of the function body. A HumanEvalFix answer written as a plain continuation of the declaration fails for these five problems in the original harness and here; a correct solution has to bring the helper itself (the reference file does).
- The `entry_point` field, which the HumanEvalFix prompt names in "Fix bugs in <entry_point>.", does not occur in the declaration of `JavaScript/114`, `Java/99`, `Java/101` and `Java/114`. The prompts are kept as they are.
- The executor is not hardened in the original harness and is not hardened here: the submitted code runs in the same program as the unit tests. For JavaScript the executor only checks that the program prints nothing, and for Java, Go, C++ and Rust it checks the exit status, so a submission that ends the program early with a success status is counted as passed; the executor is the original code, so the original harness gives the same verdict. This was confirmed through Harbor for JavaScript: a solution file containing only `process.exit(0);` gets reward 1. Python is not affected, because its tests run inside the executor's own process: a submission that exits early is scored as failed.
- What a submission cannot do was checked through Harbor with Python submissions: one that writes `/logs/verifier/reward.txt` itself, one that leaves a background process behind to write it later, and one that tries to list the tests directory all got reward 0.

**Unusable submissions.** One rule: if the solution file is missing, is not a regular file (a directory or a symbolic link), is not valid UTF-8 or is larger than 1 MiB, the verifier scores the empty generation, which is what the original pipeline scores when it has no generation for a problem. `verifier/result.json` records the case in `submission_status`. Checked through Harbor (job `hep-probe-1`, Python tasks): a directory at the solution path gets reward 0 with `not_a_regular_file`, a file that is not UTF-8 gets 0 with `not_utf8`, a file larger than 1 MiB gets 0 with `too_large`, and a symbolic link gets 0 with `missing`, because Harbor does not carry links over to the verifier. An empty file is scored as it is (`ok`, reward 0). One case gives no score at all: a solution file with mode 000 makes Harbor 0.25.0 fail the trial with a `PermissionError` before the verifier starts. The same job checked the separation of the two phases: files planted during the solving phase around a wrong answer did not change the verdict (reward 0), and code running in the scoring phase could not write the reward files, read the tests or the task directory, or resolve a host name.

**Deviations from the original setup.**

- The original harness is given model completions; here an agent writes a file. The instruction therefore adds, around the unchanged prompt, where to save the file and how it is graded. It does not name the benchmark.
- Toolchain: OpenJDK 18 (GA build 18+36) instead of the Oracle JDK; Node.js v16.14.0 (the OctoPack README names no Node.js version); NumPy 1.25.2; Rust crates pinned by a `Cargo.lock` to versions from August 2023 and compiled into the image; Go runs in GOPATH mode with cgo disabled and takes `testify` from a pinned, checksum-verified vendor bundle.
- No Go module proxy: the Go image build runs no `go get` or `go mod` command and sets `GOPROXY=off`. The images were built and the oracle run was done on a network from which `proxy.golang.org` is not reachable.
- The dataset is read with `polars` from the parquet files of the pinned revision instead of the `datasets` library.

**Resources.** Image sizes after a local build: Python 238 MB, JavaScript 251 MB, Java 354 MB, Go 480 MB, C++ 526 MB, Rust 1.17 GB. Scoring one submission in the task image takes 0.3 to 1.3 seconds and peaks at 35 to 185 MB of memory, and the container grows by 0.1 to 25 MB (measured on two tasks per language). In the full oracle run a trial took 21 to 22 seconds in every language (median; 26 seconds at most), nearly all of it starting the two containers and setting up their network policy. Task limits: 1 CPU, 4 GB memory, 10 GB storage, 900 s for the agent.

**Not verified.** Parity experiments (none has been run); the oracle on the HumanEvalFixDocs family (see Oracle verification); any agent that solves a task with a model (`claude-code` was only started with an invalid key, see the parity plan); environment providers other than local Docker on x86-64; the arm64 variants of the images, whose download checksums are in the Dockerfiles but which were never built; the registry commands.

## Troubleshooting

- **A trial fails with an environment-start or timeout error on a loaded host.** This is infrastructure noise; run those trials again with `harbor job resume -p jobs/<job-name> -f <ErrorType>`.
- **The agent cannot reach its model endpoint.** On a host whose Docker daemon is configured with its own DNS server, an agent cannot resolve its model endpoint through Harbor's egress sidecar. Add `--extra-docker-compose <file>` to the run with a compose file that sets `network_mode: bridge` for the `harbor-docker-egress-control-sidecar` service.
- **The agent uses another model backend than expected.** Provider-selection variables in the launching shell (for example `CLAUDE_CODE_USE_BEDROCK`) make Harbor's `claude-code` agent use that backend; unset them before the run.
- **`humanevalpack-score` exits with status 1.** Some trials have no verifier result; the message lists them. Run them again, or pass `--allow-unscored` for partial numbers.
- **The generator reports an incomplete task directory or a second run.** Run it again with `--overwrite`, or wait for the other run to finish.
- **A trial has no verifier result and a `PermissionError`.** The agent made the solution file unreadable (mode 000); Harbor 0.25.0 cannot collect it.
